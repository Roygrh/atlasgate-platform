# Target-Role Evidence Map

This reusable map connects competencies expected of an enterprise Java API platform architect with evidence that AtlasGate can produce. Planned evidence is directional; it must move to implemented evidence only after the repository contains validated artifacts or behavior.

| Competency | Planned evidence | Implemented evidence |
| --- | --- | --- |
| API platform ownership | Product boundaries, capability roadmap, lifecycle governance, and measurable platform outcomes | Fictional company context, stakeholder model, engagement plan, evidence taxonomy, and unresolved outcome questions in `docs/discovery/` |
| Java and Spring engineering | Modular control-plane modules with explicit ports, adapters, tests, and documented framework choices | Not implemented yet |
| Gateway architecture | Component-oriented gateway runtime, extension boundaries, policy execution, and traffic-flow validation | Not implemented yet |
| High-performance APIs | Explicit latency and throughput targets, repeatable benchmarks, profiling evidence, and capacity decisions | Not implemented yet |
| Security and governance | Threat modeling, secure configuration, identity and access controls, policy governance, and negative-path tests | Not implemented yet |
| Observability and reliability | Service-level objectives, telemetry conventions, failure-mode tests, dashboards, and operational runbooks | Not implemented yet |
| Architecture communication | Decision records, current-state and target-state views, trade-off narratives, and reconstruction documentation | Architecture documentation entry point, ADR governance and template, and reproducible Build from Zero chapters; no architecture baseline or diagram exists |
| Testing strategy | Risk-based test pyramid, contract and integration coverage, security checks, and failure-path validation | Not implemented yet |
| Deployment portability | Reproducible packaging, environment-neutral configuration, local validation, and deployment options based on requirements | Not implemented yet |
| Technical leadership | Iteration records, reviewable decisions, engineering standards, mentoring guidance, and evidence of managed trade-offs | Repository guidance, factual iteration ledger, discovery planning, stakeholder trade-off model, stable risk register, and decision review rules |

## Foundation evidence

The current repository also demonstrates documentation-only foundation practices: English tracked artifacts, private-context isolation, reconstruction guidance based on observable state, stable uncertainty and risk identifiers, and explicit separation among stakeholder statements, findings, assumptions, hypotheses, requirements, and decisions. These artifacts are governance evidence, not evidence of implemented platform behavior.
